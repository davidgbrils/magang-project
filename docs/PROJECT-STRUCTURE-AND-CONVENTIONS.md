## 2. Naming

- React components: `PascalCase`, for example `FileDropzone.tsx`.
- Functions and variables: `camelCase`.
- Python modules: `snake_case`.
- Database tables and columns: `snake_case`.
- API JSON: `camelCase`.
- Enum values: uppercase, for example `REVIEW_REQUIRED`.
- Routes: lowercase kebab or existing framework convention.
- Tests: behavior-oriented names, for example `selects_latest_passed_mos_test.py`.
- Migration names: timestamp generated by the Supabase CLI, followed by a descriptive slug.

## 3. Code style

- TypeScript strict mode.
- No `any` unless boundary data is immediately validated.
- Validate external input at the boundary with schemas.
- Keep domain matching logic independent from HTTP and UI.
- Keep workbook I/O independent from matching rules.
- Keep UI components independent from Supabase service-role operations.
- Prefer small functions with one responsibility.
- Do not hide unexpected exceptions behind blanket `try/catch` or plausible zero values.
- Use explicit result statuses and reasons.
- Add comments only for non-obvious business rules. Do not add generic comments.

## 4. UI conventions

- All user-facing copy is Bahasa Indonesia.
- Technical identifiers such as MOS, MCF, SITASI, Certiport, NIM, XLSX, and CSV remain unchanged.
- Use `#e0e0e0` as the neumorphic base surface.
- Use raised, recessed, and pressed states consistently.
- Use text plus icon for statuses, not color alone.
- Every form field has a label and validation message.
- Every interactive component has default, hover, focus, pressed, disabled, loading, and error states where relevant.

## 5. Git workflow

Branches:

```text
main
├── feat/frontend-itcc-wisuda-sync
├── feat/backend-itcc-wisuda-sync
└── test/itcc-wisuda-sync
```

Each branch uses its own worktree. Do not edit another agent's owned area.

Recommended sequence:

1. Create an issue or task with acceptance criteria.
2. Create a branch/worktree.
3. Inspect baseline and run tests.
4. Implement one coherent change.
5. Run focused tests, lint, typecheck, and build as applicable.
6. Commit focused changes.
7. Review diff and report evidence.
8. Merge only after the branch is verified.

Commit format:

```text
<type>(<scope>): <imperative summary>
```

Allowed types: `feat`, `fix`, `test`, `refactor`, `docs`, `chore`.

Examples:

```text
feat(matching): apply MCF eligibility by program code
feat(excel): preserve all graduation workbook sheets
test(excel): verify only ITCC columns change
docs(api): document synchronization endpoints
```

Do not commit `.env`, real source workbooks, generated files containing personal data, or service credentials.
